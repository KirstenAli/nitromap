One small library

More than an in-memory map.

NitroMap keeps the common path direct while adding the storage and query capabilities that embedded applications usually have to assemble themselves.

01 Persistence

Writes stay fast. Disk work moves aside.

Mutations update memory first. A background writer coalesces changed keys, serializes the latest state, and forces each batch once.

put → dirty key → batched log
02 Familiar API

A real ConcurrentHashMap.

Use the API Java developers already understand. Reads remain direct, concurrent, and entirely in memory.

03 Query engine

Ask more of your map.

Filter, join, group, aggregate, order, and limit records with a focused SQL-like language.

SELECT city, SUM(total)
FROM orders
GROUP BY city
04 Shared nothing

Scale memory and compute across processes.

Stable logical partitions route each key to exactly one owner. No replica, quorum, or hidden fallback copy.

ABC
05 Built-in REST

Integration without a framework.

Expose one or many named maps using Java's built-in networking, with authorization and filter hooks.

PUT/maps/customers/entries/{key}
06 Bounded memory

Stay in control under pressure.

Opt into background eviction, bounded query operators, and disk spill for larger joins, groups, and sorts.

Designed around the hot path

The application thread does less.

A persistent mutation changes the map, marks the key, and returns. Serialization and file I/O happen on the background writer.

  • ✓Repeated changes coalesce before disk
  • ✓One force-to-disk operation per batch
  • ✓Torn final records are discarded safely
  • ✓Atomic manual log compaction

SELECT c.city, c.name,
       COUNT(*) AS order_count,
       SUM(o.total) AS total_sales,
       AVG(o.total) AS average_order,
       MIN(o.total) AS smallest_order,
       MAX(o.total) AS largest_order
FROM customers c
JOIN orders o ON c._key = o.customerId
WHERE (c.city = :primaryCity
       OR c.city = :secondaryCity)
  AND c.score >= :minimumScore
  AND o.total >= :minimumOrder
GROUP BY c.city, c.name
ORDER BY total_sales DESC, average_order DESC
LIMIT 20

Shared-nothing clustering

Distribute the data, not copies of it.

Stable FNV-1a hashing maps every key to a logical partition and one configured owner. Each node remains an ordinary local NitroMap with its own persistence.

01

Zero replicationNo quorum, replica, or fallback read.

02

Bounded distributed SQLStreamed scans, hash shuffles, partial aggregation, and disk spill.

03

Explicit failureIf an owner is unavailable, its partitions fail instead of returning stale data.

Clear tradeoffs

Small enough to understand.
Honest enough to trust.

01Asynchronous by designRecent writes can be lost on hard termination before the next disk batch.

02No hidden availability storyCluster owners hold the only copy. Losing a node loses access to its partitions.

03Focused SQL, not a database disguiseNo transactions, outer joins, subqueries, or cluster-wide snapshots.
